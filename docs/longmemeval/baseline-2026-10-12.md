# LongMemEval retrieval baseline (2026-10-12)

Retrieval quality of the memory search (`searchMemoryWithScreening` in `packages/extracted/screening/memorySearch.ts`) measured on LongMemEval (Wu et al., ICLR 2025). Measured on this repository with the 4th search layer (`log-archive`) in place; later search changes should be compared against these numbers.

## Reproduce

```sh
cd packages/daemon
npm run eval:longmemeval -- --set s        # tables go to stdout; use --set oracle for the oracle set
```

The data lives in `longmemeval/data/` at the repository root (gitignored).

```sh
curl -L -o longmemeval/data/longmemeval_oracle.json https://huggingface.co/datasets/xiaowu0162/longmemeval/resolve/main/longmemeval_oracle
curl -L -o longmemeval/data/longmemeval_s.json      https://huggingface.co/datasets/xiaowu0162/longmemeval/resolve/main/longmemeval_s
```

The run is deterministic: the same input produces the same stdout.

## Conditions

| Item | Value |
|---|---|
| Data | HF `xiaowu0162/longmemeval` — `longmemeval_s` sha256 `08d8dad4…e117894`, `longmemeval_oracle` sha256 `821a2034…20c` |
| Ingestion | Per question, a throwaway temp dir receives L3 daily logs `logs/YYYY/MM/YYYY-MM-DD.md`, **one session per day file**. Sessions keep their `haystack_dates` order and HH:MM, but are dated one day apart counting back from the day before question_date (real dates collide within a day). One message = one line `- [HH:MM] [longmemeval] <content>`, newlines replaced by spaces. `index.json` is empty |
| Search | `searchMemoryWithScreening(dir, question, { threshold: searchThreshold=0.10, maxResults: searchMaxResults=20 })`, the same config as the production gate (`DefaultBm25ScreeningGate`). Layers: index.json entries (empty) → .md files → log lines of the last 48h → all-time log lines `log-archive` (only when the upper three layers return fewer than maxResults) |
| Gold | Sessions containing a `has_answer === true` message (labels unmodified). A file hit counts for the session of that day file, a log-line hit for the session of that line. Both are session-level recall, matching the LongMemEval standard |
| Clock | `real` = wall clock (2026-10). `qdate` = `Date.now()` pinned to question_date (equivalent to moving the logs to "today") |
| Metrics | Recall@k = share of questions with at least one gold session in the top k. MRR = reciprocal rank of the first gold hit (0 if none). `_abs` questions are excluded from Recall/MRR |
| Chance | Expected Recall@k when sessions are ranked at random (analytic) |
| Runtime | About 63 s for the 500 `_s` questions, about 11 s for oracle (Windows 11, Node 22) |
| Not measured | Distillation (LLM) and end-to-end answer accuracy |

## Results — `longmemeval_oracle` (500 questions, sanity check; the haystack holds only gold sessions)

Overall (470 non-abstention questions): real R@5 0.994, R@10 0.996, MRR 0.982; qdate R@5 0.996, R@10 0.996, MRR 0.983. Chance is 1.000 for both. The share of `_abs` questions answered with 0 results is 0.000. Results from `log-archive`: real = 5738, qdate = 1617.

## Reading

- At session level, `_s` R@5 is 0.957 against a chance of 0.172. The weakest types are single-session-preference (MRR 0.551) and temporal-reasoning (MRR 0.851).
- `real` and `qdate` match on `_s`: the .md file layer scores all 50 sessions with BM25, so the 48h window does not show up in the ranking.
- Abstention does not work: every one of the 30 `_abs` questions returns some result.

## Known limits

- **Synthetic dates.** Sessions are spaced one day apart, so the real gaps in `haystack_dates` are lost. Retrieval difficulty for date-driven temporal-reasoning questions differs from real data.
- **48h window.** The recent log-line layer returns nothing under `real` (the data is dated 2023). Under `qdate` only the last one or two sessions fall inside the window.
- **File truncation.** The file layer reads only the first 100KB of each file (`MAX_FILE_BYTES`).
- **No distillation.** `index.json` is empty. In production the entry layer built by nightly distillation does most of the work, and only day files newer than `.last-distill` remain for the file layer. These numbers describe a memory holding only undistilled logs; since the file layer sees every session here, the contribution of `log-archive` comes out small.
- **English only.** LongMemEval dialogues are in English; performance on memories in other languages is not represented.
- **No answer accuracy.** Returning the gold session does not show whether an LLM reading it answers correctly.
